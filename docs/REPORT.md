# UQAB — report skeleton

This is the structure the written report should follow, with the tables the code
already produces and the sentences that must be honest about what was measured.
Do not type numbers by hand: `python scripts/demo.py --loads 20 --idle 2 --repeats 3`
runs the whole A/B/C protocol and writes `docs/report/sample-results.md` (+
`.json`); `python -m experiments.report --out docs/report/results.md` renders the
same tables from whatever is already stored in `data/uqab.sqlite`.

---

## 1. Introduction

UQAB is a Tor pluggable transport that hides *when* a user is browsing. Real Tor
traffic is bursty: pages load, then nothing happens until the next click. An
observer who cannot read the traffic can still classify one-second windows as
ACTIVE or IDLE and learn a lot from that rhythm. UQAB replaces the rhythm with a
*persona*: a timetable of fixed-size records whose size and pacing change between
states according to a learned or generated policy, so the record stream no longer
mirrors what the user is doing.

Research question:

> Does persona-driven cover traffic reduce an observer's ACTIVE/IDLE inference
> accuracy, compared with plain Tor and with constant-rate cover, and what does
> that cost in latency and overhead?

## 3. Design summary

Three paragraphs, one per layer:

1. **The shaped channel.** One TLS 1.3 connection between the PT client and the
   PT server; inside it, frames (`type | length | payload`) are packed into
   records of exactly `record_size` bytes at slots of `slot_ms`. DATA frames go
   first, one PADDING frame fills the rest, one `write()` per record. Any
   violation closes the tunnel (fail-closed).
2. **The persona timetable.** A persona is a small state machine: states carry
   `record_size`, `slot_ms` and a duration range; transitions are probabilities.
   The scheduler walks it, gives every state a floor rate, and limits
   `record_size × 1000 / slot_ms` to a configured maximum. The same scheduler runs
   in the client (uplink) and the server (downlink).
3. **The app.** A Min-derived Electron shell with a single Start/Stop control, a
   1 Hz panel, and a hard gate: the tab session is pinned to the engine's SOCKS5
   port and every request is cancelled unless the engine reports a live session.

Use `docs/DESIGN_DECISIONS.md` (D1–D20) for the decisions that need justifying —
especially the greeting record (D5), the plain-Python classifiers (D8), the
slot-log capture (D9) and the Min deviation (D12).

## 4. Experiment method

* **Configurations.** A plain Tor; B constant-rate cover (`constant` persona);
  C persona cover (`high`, or a persona generated by the local LLM / learned from
  the user's own browsing).
* **Timeline.** A scripted browsing session: page loads alternating with IDLE
  dwell time, identical for all three configurations. Each phase duration carries
  `experiments.jitter_s` (400 ms) of uniform jitter so labels never align with the
  1 s analysis grid, and one ACTIVE phase is a page view — up to
  `experiments.requests_per_load` sequential requests (document + subresources)
  spread over the phase — so ACTIVE windows really contain traffic. The demo
  origin paces its body in 1 KiB chunks, which is what gives a loopback page a
  realistic load time. Each configuration is run `--repeats` times (seeds differ)
  so the table shows run-to-run variance, not one lucky split.
* **Observer.** One-second windows with eight features (packets, bytes, mean and
  variance of packet size, mean and variance of inter-packet gap, uplink ratio,
  burst count), labelled from the runner's ground truth. Two classifiers
  (logistic regression, random forest), 5-fold stratified cross-validation,
  percentile bootstrap 95% CI for F1.
* **Metrics.** Accuracy and F1 of the ACTIVE class, page-load latency (median,
  p95), cover overhead (wire bytes per page byte), slot timing error (p50/p95).

Commands:

```bash
python scripts/demo.py --loads 20 --idle 2 --repeats 3   # lab, writes the tables
python -m experiments.compare --loads 20 --repeats 3     # lab, console only
python -m experiments.compare --loads 20 --no-lab        # real Tor on 127.0.0.1:9150
python -m experiments.report --out docs/report/results.md
```

## 7. Threats to validity

Say all of this plainly:

* Lab runs have no Tor circuits and no real network conditions; absolute F1 values
  are optimistic. Only the relative ordering of A/B/C in the *same* environment is
  meaningful.
* Configuration A in lab mode is a plain relay (D7), not a Tor circuit.
* The observer is link-level only: no timing side channels beyond 1 s windows, no
  packet-level machine learning, no long-term correlation.
* A single scripted timeline; real users browse differently and for longer. The
  jitter and page-view load model (D19) remove the two worst artefacts — grid-
  aligned labels and empty ACTIVE phases — but they do not turn a script into a
  user.
* Lab "packets" are records: sizes are byte-faithful to `record_size` (D20) but a
  real capture would show MTU-sized segments carrying slices of the TLS stream,
  so size-distribution features are not directly comparable to a real observer.
* Fixed slot rates mean a slow page load delays real data rather than changing the
  record rate — this is by design, but it costs latency.
